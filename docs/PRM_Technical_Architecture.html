System / Background Use Cases
Background Scheduler
Runs at configurable intervals. Recomputes employee utilisation %, updates employee status (BENCH / ALLOCATED), flags project health risks, marks timesheets as MISSED for incomplete weeks.
AI Skill Matcher
Receives natural language requirement from Manager. Pre-filters ineligible employees. Sends candidate summary + requirement to LLM. Returns ranked list with reasons.
AI Risk Summariser
Collects milestone dates/status, logged hours, allocation data for a project. Sends structured facts to LLM. Returns plain-English risk paragraph for Manager review.

Application Workflow
End-to-end user journeys and system processes
Admin Workflow
1

Initial Bootstrap

Seed script inserts first admin account with default credentials (admin / Admin@1234). On first login, admin is forced to change password before accessing any screen.

2

Create User Account

Admin goes to Manage Users → Create User Account. Sets role, temp password. New user gets forcePasswordChange=true.

3

Create Employee Profile

Admin goes to Manage Employees → Add Employee. Links the user account by userId. Employee starts with status BENCH.

4

Configure Skills

Admin adds skills to employee with category (Backend/Frontend/DevOps/QA) and proficiency (Beginner/Intermediate/Advanced).

5

Create Projects

Admin creates project with name, dates, status, and assigns a Manager. Adds milestones with due dates.

6

Configure System

Admin sets LLM provider (Gemini/Groq), API key, scheduler interval, and max weekly hours.

Manager Workflow
1

View Resource Dashboard

Manager sees bench employees with skills and partially-allocated employees with free capacity. Can drill into any employee for full profile.

2

AI Resource Search

Manager types natural language requirement. Backend pre-filters fully-booked employees. Sends eligible candidates + requirement to LLM. Receives ranked results with reasons.

3

Confirm Allocation

Manager picks candidate from AI results (or enters employee ID directly). Sets utilisation %, from/to dates. Server validates total doesn't exceed 100%.

4

Monitor Projects

Manager views My Projects — health traffic-light status per project. Drills in to see milestone progress, allocated team, risk flags computed by scheduler.

5

AI Risk Summary

Manager requests AI narrative for a project. Backend collects milestone + timesheet data, sends to LLM, displays plain-English paragraph with risk assessment.

6

Timesheet Oversight

Manager filters team timesheets by week. Views SUBMITTED vs MISSED status per employee per project. Read-only — no approve/reject action.

Employee Workflow
1

Login & Reminder Check

After login, system checks if the most recent completed week's timesheet is missing. If so, warning banner is shown on the employee menu.

2

Submit Weekly Timesheet

Employee selects week (defaults to last Monday). For each active project allocation that week, enters hours worked and selects activity tags from a fixed list (or types custom).

3

Server Validation

Backend checks: hours ≤ (allocation% × max weekly hours), total ≤ max weekly hours, no duplicate for same week, no future week submissions.

4

View History

Employee can view all past weeks with SUBMITTED/MISSED status. Can drill into any submitted week to see project breakdown and activity tags.

Background Scheduler Workflow
1

Trigger (Configurable Interval)

Node-cron fires based on admin-configured interval (default 4 hours). Three jobs run in sequence to avoid data inconsistency.

2

Compute Utilisation

For each employee, sums utilisation % of all allocations where fromDate ≤ today ≤ toDate && isActive=true. Updates currentUtilisation and sets BENCH/ALLOCATED status.

3

Flag Project Health

For each ACTIVE project: checks overdue milestones (IN_PROGRESS past dueDate), checks logged hours vs expected (allocation% × maxWeeklyHours) per resource. Sets AT_RISK / ATTENTION / ON_TRACK.

4

Mark Missed Timesheets

For each employee with at least one active allocation, checks if a timesheet exists for last completed week. If not, inserts a MISSED record. This enables the reminder banner and manager visibility.

SOLID Principles — Where Applied
S — Single Responsibility Principle
Each controller handles one resource group (UserController, EmployeeController, ProjectController, TimesheetController, AIController). Scheduler is separated into three single-purpose jobs (computeUtilisation, flagProjectHealth, markMissedTimesheets).
Example: EmployeeController only handles employee CRUD — skill management is in a separate SkillController.
O — Open/Closed Principle
LLM service uses Strategy Pattern — GeminiAdapter and GroqAdapter both implement ILLMAdapter interface. Adding a new LLM provider (e.g. OpenAI) requires adding a new adapter class without modifying existing code.
Example: src/services/llm/ILLMAdapter.js, GeminiAdapter.js, GroqAdapter.js.
L — Liskov Substitution Principle
GeminiAdapter and GroqAdapter are interchangeable wherever ILLMAdapter is expected. The AIService constructor takes any ILLMAdapter — it never checks which concrete class it received. The scheduler jobs can be swapped with mock implementations in tests.
Example: new AIService(new GeminiAdapter(apiKey)) vs new AIService(new GroqAdapter(apiKey)).
I — Interface Segregation Principle
IEmployeeRepository and IProjectRepository are separate interfaces. Admin and Manager use different subsets of employee-related methods — AdminEmployeeService uses the full interface, while ManagerResourceService uses a narrower read-only IResourceReader interface.
Example: Manager routes import ResourceService, not AdminEmployeeService — they never gain access to deactivate/update methods.
D — Dependency Inversion Principle
Controllers depend on service interfaces, not concrete service classes. Services depend on repository interfaces, not Mongoose models directly. Config is injected at startup — no hardcoded database connections inside business logic.
Example: AllocationController(allocationService: IAllocationService) — testable without a real database.
Design Patterns Used
Repository Pattern
All database operations abstracted behind repository classes (UserRepository, EmployeeRepository, AllocationRepository, TimesheetRepository). Controllers and services never call Mongoose directly.
Strategy Pattern — LLM Adapter
LLM provider (Gemini/Groq) selected at runtime from system_config. AIService holds a reference to the current ILLMAdapter. Admin can switch providers without restarting the server.
Singleton Pattern — DB Connection
MongoDB connection is established once and reused across the application. DatabaseManager class ensures a single connection pool is shared.
Factory Pattern — Router Setup
routerFactory(role) creates role-specific Express routers with appropriate middleware chains. Ensures role guards are always applied consistently — no risk of forgetting auth middleware on a new route.
Observer Pattern — Scheduler Events
SchedulerEventEmitter broadcasts events after each job completes (utilisationComputed, healthFlagged, timesheetsMissedMarked). Logging and future webhook notifications subscribe to these events without modifying the scheduler jobs.
Adapter Pattern — LLM Provider
Wraps different LLM APIs (Gemini REST, Groq REST) behind a uniform interface: suggest(prompt: string): Promise<string>. Hides provider-specific request formats and response parsing.
Design Principles Applied
DRY — Don't Repeat Yourself
Allocation overlap validation logic written once in AllocationService and called by both the AI-assisted path and the direct allocation path. Zod schemas defined once and reused on frontend + backend. weekStart normalisation (always Monday) is a single utility function.
Separation of Concerns
Clear layering: Routes → Controllers → Services → Repositories → Database. Frontend: Components → Hooks (API calls) → Store (auth state). Scheduler is a completely independent module — not tangled with the API layer.
Fail Fast
Allocation creation validates over-allocation synchronously before calling any LLM. Timesheet submission validates hours limits before persisting. If any validation fails, the request is rejected immediately with a descriptive error — no partial writes.
YAGNI — You Aren't Gonna Need It
No approve/reject timesheet workflow built (BRD says read-only for managers). No notifications system built speculatively. No multi-org support. The system solves exactly what the BRD asks for.
